# 车载（Onboard / 前视 dashcam）场景的数据集选择

## 1. 结论

| 角色 | 数据集 | 理由 |
|---|---|---|
| **★ 主数据集** | **BDD100K（Tracking 子集，box_track_20）** | 唯一的"车载前视 + 多类别（车/人/骑行）+ 40 s 长序列 + 夜/雨/城/高速场景多样"组合 |
| **★ 必加补充** | **KITTI Tracking（train 21 条）** | 车载前视 10 Hz 连续视频；**有相机标定 + 3D 真值 → 可输出米制轨迹/速度/航向**（车联网状态消息的唯一来源） |
| 压力测试（可选） | MOT17（train 7 条） | 行人密集 + 重度遮挡下的 ID 维持极限测试；**非车载视角，不能代表车辆结论** |
| ❌ 暂不用 | nuScenes / Waymo / Argoverse | 3D 检测为主、标注仅 2 Hz、需注册授权、体量 300 GB+；除非要做多相机/BEV 融合 |

**一句话**：车载场景用 **BDD100K 主打 + KITTI Tracking 补高帧率与米制真值**，MOT17 只当行人的压力测试。

## 2. 三者对比（按车载视角的关切排序）

| 维度 | BDD100K | KITTI Tracking | MOT17 |

| 标签帧率 | **5 fps**（40 s→203 帧）❌ | **10 Hz** ✅ | 14/25/30 fps ✅ |
| 图像尺寸 | 1280×720 | 1242×375（宽幅、窄高，物体易截断） | 1920×1080 / 640×480 |
| 类别 | car/truck/bus/train/motor/bike/pedestrian/rider（8 类）✅ | Car/Van/Truck/Pedestrian/Person_sitting/Cyclist/Tram/Misc ✅ | 仅 Pedestrian ❌ |
| 车辆占比 | 高（车辆框约占 86%）✅ | Car+Van+Truck ≈ 68% ✅ | 0% ❌ |
| 轨迹 ID | ✅ | ✅ | ✅ |
| 序列数 / 帧数 | 1600×200 = 32 万帧（选 40 条用） | 21 序列 / **8 008 帧** | 7 序列 / 5 316 帧 |
| GT 框数 | 选 40 条约 15 万框 | **47 262**（+18 039 DontCare） | 112 297（+19 750 ignore） |
| 轨迹长度 | 长（≈200 帧/序列，40 s 连续）✅ | **短：中位 33 帧（3.3 s）**，≥120 帧仅 9% ❌ | 中位 103 帧，≥120 帧 45% ✅ |

| 场景多样性 | ✅ 白天/夜间/黄昏/雨/城市/高速 | ❌ 德国 Karlsruhe 城区白天为主 | ❌ 欧洲步行街/广场 |
| 下载量 | 1.5 GB（按帧直取） | **15.8 GB**（image_2）+ 2.3 MB 标签 + 90 KB 标定 | 5.86 GB |

KITTI 实测（`data_tracking_label_2.zip` 已下载并统计）：
- 21 条 train 序列、8 008 帧、**47 262 个 GT 框、917 条轨迹**
- 类别：Car 27 300 / Pedestrian 11 470 / Van 3 301 / Cyclist 1 938 / Truck 1 189 / Misc 793 / Person 676 / Tram 595
- 密度 2.7~15.0 目标/帧；框高中位 60 px；`DontCare` 18 039 个（占全部框的 27%，评测需忽略）
- 单序列最长 0019（1059 帧 / 8826 框）、0020（837 帧 / 6845 框）

## 3. 为什么车载场景一定要加 KITTI

你的目标是"输出目标轨迹，为**车联网运动目标状态感知**提供信息"，这条链路缺两样东西，而 BDD100K 都给不了：

1. **真实时间轴**：BDD 跟踪帧只有 5 fps，`px/frame → px/s` 的换算很粗；KITTI 是 10 Hz，且 `frame → 绝对时间` 明确，速度/加速度才可信。
2. **米制尺度**：KITTI 提供 `calib`（P2 内参 + 外参）+ 3D 真值（尺寸、位置、朝向）→ 可以把像素框反投影到**自车坐标系（米）**，输出 V2X 状态消息所需的 `pos[m] / vel[m/s] / acc / heading[deg]`。BDD100K 无标定，最大只能给"归一化像素坐标 + 相对位移"，做 BEV 时需要额外假设（路面平面 + 自车俯仰角），误差不可控。

副产品：KITTI 与 BDD 帧率不同（10 Hz vs 5 Hz），正好构成"帧率 → IoU 关联难度 → IDSW"的对照；MOT17（30 Hz）再加一档，三档帧率对比很有说服力。

KITTI 的两个短板要提前处理：
- **轨迹短**（中位 33 帧）→ 不适合评"长时 ID 维持"，这项结论靠 BDD（200 帧/序列）；
- **遮挡标注稀疏** → 不适合评"遮挡后重连"，这项结论靠 MOT17。

三者互补，不重叠。

## 5. 三套数据集的分工（写进报告的表格）

| 结论项 | 用哪个数据集得出 | 数据集承担的角色 |
|---|---|---|
| 多类别（car/truck/bus/pedestrian/rider）检测 mAP | BDD100K | 精度主力 |
| 长时序（40 s）持续跟踪、轨迹生成、ID 维持率 | BDD100K | ID 维持主力 |
| 夜间/雨天/高速等场景鲁棒性 | BDD100K（亮度启发式分层） | 场景多样性 |
| **10 Hz 实时性、延迟/帧耗时预算** | KITTI Tracking | 速度主力 |
| **米制轨迹、真实速度/航向、V2X 消息字段** | KITTI Tracking（calib+3D） | 状态感知主力 |
| 帧率敏感性（5 / 10 / 30 Hz 三档） | BDD + KITTI + MOT17 | 三档对照 |
| 重度遮挡下的 ID 重连（ReID/CMC/插值收益） | MOT17（辅助：BDD 遮挡标记） | 压力测试 |
| 车辆类别结论 | **BDD100K + KITTI**（MOT17 不可用） | — |

## 6. 风险

| 风险 | 应对 |
|---|---|
| KITTI `DontCare` 占 27%，若不 ignore 会虚高 FP | 评测脚本强制 ignore（TrackEval 支持 KITTI 格式） |
| KITTI 标签中重度遮挡目标缺失 → 关联器"看起来"很好 | 结论中明确说明；遮挡结论只引用 MOT17 |
| KITTI 宽幅 1242×375，letterbox 到 640 后垂直方向分辨率损失大 | 输入用 `imgsz=960` 或按宽边缩放（`rect=True`），并做 640/960 对比 |
| BDD 5 fps 导致的 IoU 关联困难被误读为"跟踪器差" | 用 KITTI/MOT17 做同参数对照，明确归因于帧率而非算法 |
| 15.8 GB 下载中断 | 支持 `curl -C -` 续传；已下 2.3 MB 标签可先做数据选择与格式转换，不等图片 |
